# 用户 · 用户组 · 角色 · 权限 的联动设计

> 本文回答一个问题：**用户管理、用户组、权限配置这三块怎么才能联动起来，而不是各配各的。**
>
> 现状问题（用户原话）：「角色呀之类的，然后都不能进行联动」「两边的权限分开配置，这样是不合理的」。

## 1. 先定性：四个概念各管一件事

业界（NIST RBAC / Keycloak / AWS IAM / 飞书）的共识是——**这四个东西不能互相替代**，各自职责必须分清：

| 概念 | 回答的问题 | 一句话 |
|---|---|---|
| **权限点** `permission` | 系统能做哪些动作 | 代码里的受控枚举，只能随发版新增 |
| **角色** `role` | 「能做什么」 | 一组权限点的集合，可自定义、可继承 |
| **用户组** `group` | 「是谁、属于哪一批」 | 一批人 + 数据范围 + 有效期 |
| **用户** `user` | 具体的一个人 | 属于某个组，可额外直挂角色 |

**关键判断：权限点只挂角色，不挂用户组。**
理由（调研原文）：组如果直接挂权限，会导致「同一个角色的人在不同组里能力不同」，在阅卷、成绩发布这类合规敏感场景几乎必然引发审计争议。Entra ID 允许组挂角色，但上了极重的锁（组类型建时不可改、单租户限 500、禁止动态组、禁止嵌套），说明这是**特权设施而非日常开关**。

所以：**用户组可以拥有角色，但不能拥有权限。**

```
用户 ──属于──> 用户组 ──拥有──> 角色 ──包含──> 权限点
  └────────────直挂────────────────┘
```

## 2. 数据模型（改造后）

| 表 | 作用 | 关键字段 |
|---|---|---|
| `t_user` | 用户 | `dept_id`（**主组**，数据可见范围仍按它算） |
| **`t_user_dept`**（已建） | **用户 → 附加组** | `user_id`、`dept_id`；一人可属于多个组，最终所属组 = 主组 ∪ 附加组 |
| `t_dept` | 用户组（树） | `parent_id`、`valid_from`、`valid_to` |
| `t_role` | 角色 | `code`、`authority`（权限串） |
| **`t_dept_role`**（已建） | **组→角色绑定** | `dept_id`、`role_id` |
| `t_user_role` | 用户→角色（已有） | `user_id`、`role_id` |
| `t_repo_partner` / `t_project_partner` | 数据授权 | `user_id` 或 `dept_id` |

**已删除**：`t_dept.authority` 与 `t_dept.authority_mode`（INHERIT/APPEND/OVERRIDE 那套组级权限覆盖）。
列已由 `scripts/dev/drop-dept-authority.sql` 删除，`init-mysql.sql` / `init-h2.sql` 同步去掉了列定义，
实体 / DTO / 前端字段一并清理。**权限 = 角色，组只负责「成员 + 有效期」**，`t_role.authority` 保留不动。

### 生效规则（唯一事实来源，已实现）

```
最终权限 = 用户直挂角色（t_user_role）的权限
         ∪ 所属组（主组 ∪ 附加组，各自沿祖先链展开）绑定角色（t_dept_role）的权限
         ∪ ROLE_* 身份标记
最终可见数据 = 个人授权 ∪ 组授权（含祖先组）   ← 数据可见范围仍只按主组，附加组尚未接入（见文末）
能否登录   = 组链上任一组的有效期窗口内（valid_from ≤ now ≤ valid_to，空表示不限）
```

- 实现位置：`UserServiceImpl#loadUserById`（`resolveUserAuthorities` + `resolveDeptChainIds`），
  `assertDeptValid` 也走同一条组链；组表整表取一次、`t_dept_role` 按整条组链 `in` 一次，无 N+1。
- 权限缓存：`loadUserById` 结果按 user 缓存在 `userCache`；组角色变更时
  `DeptServiceImpl#saveDeptRoles` 会在事务提交后清空 `userCache`，否则改角色不生效。
- 组绑角色等于批量给组内所有人授权，因此 `saveDeptRoles` 有提权保护：非管理员只能绑定
  「自己已拥有的权限」的子集，且任何人都不能把超级管理员角色绑到组上。
- 超级管理员 `ROLE_admin` 始终全权限，不受任何组策略影响。

## 3. 界面怎么联动（三块菜单各配什么）

### 3.1 系统管理 → 角色权限（定义「能做什么」）
- 角色列表：内置角色（超级管理员/老师/学员）只读，可新增自定义角色（如「教研组长」「校区负责人」）。
- 选中角色 → 右侧权限矩阵勾选 → 保存回 `t_role.authority`。
- **新增角色后，立刻可以在用户组和用户管理里被选中**（这就是"联动"的关键）。

### 3.2 系统管理 → 用户组（定义「哪批人 + 什么角色 + 多久」）
一个组的配置页包含四块，**不再出现"权限串"输入框**：

```
① 基本信息   名称 / 上级组 / 排序
② 角色       选择该组拥有哪些角色（可多选）→ 写 t_dept_role
③ 有效期     起止时间，默认永久；决定组员能否登录
④ 数据授权   这个组能看哪些题库/考试（复用现有 t_repo_partner / t_project_partner）
```
- 组树**默认全部展开**，不折叠。
- 列表每行显示：组名 · 绑定角色（标签）· 有效期（永久 / 2026-01-01 ~ 2026-06-30 / 已过期）。

### 3.3 系统管理 → 用户（定义「这个人」）
用户编辑弹窗里，角色一栏要**分成两块显示**：
- **继承角色（只读）**：来自所属组的角色，灰底标签，提示「来自用户组：育婴五级班」
- **额外角色（可编辑）**：直接授给这个人的角色 → 写 `t_user_role`

这样管理员在用户页就能一眼看出"这个人的老师权限是从组来的还是单独给的"，不会出现
「在组里配了角色，用户页却看不到、以为是没生效」的困惑。

## 4. 有效期怎么执行（不只是显示）

1. **登录时**：`loadUserByUsername` 解析用户所属组链（主组 + 附加组 + 各自祖先组），
   若当前时间不在窗口内，抛明确中文错误「所在用户组「X」有效期已过（2026-06-30 截止），请联系管理员延期」。
2. **已登录用户**：JWT 有效期内仍可能过期，因此 `loadUserById`（每次鉴权都会走）也要校验——
   目前这条**还没做**（只有登录入口校验），属于遗留项。
3. **匿名答题不受影响**：公开链接 `/s/:id` 不依赖登录，有效期只管"组员身份"。
4. 组有效期**只影响登录与作答资格**，不删数据；延期后原权限自动恢复。

## 6. 与现有实现的关系

- **权限目录 API**（73 项、10 分组）与**角色权限矩阵页**（`/system/permissions`）保留，是 3.1 的实现。
- 组级权限覆盖（INHERIT/APPEND/OVERRIDE）**已下线**：`UserServiceImpl` 不再读 `t_dept.authority`，
  改为读 `t_dept_role`。用户组页面本来就没有权限串输入框，无需改 UI。
- **仍未接入：数据可见范围**。`t_repo_partner` / `t_project_partner` 的组授权、用户列表按组筛选、
  协作者候选、以及各处直接读 `t_user.dept_id` 的 SQL，都还只认**主组**；附加组目前只影响
  「角色/权限继承 + 组有效期」，看不到附加组被授权的题库与考试。

## 7. 需要你确认的三点（已按建议默认执行）

1. **用户能否同时属于多个组？** 建议允许（老师可能既带五级班又带四级班），权限取并集。
2. **组有效期过期后**：只禁止登录，还是连已收集的答卷也要冻结？（建议只禁登录）
3. **自定义角色上限**：是否限制只有管理员能创建自定义角色？（建议是）
