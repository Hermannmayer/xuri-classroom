# AI 编码规则

> 这是给 AI 助手的编码规则细则；入口是本仓库根目录的 AGENTS.md 第 0 节（该文件含本地环境信息，默认不入库）。
> 只约束新增和本次改动的代码，不追溯历史注释或历史测试。

## 1. 先复用，再实现

### 1.1 决策顺序

默认假设：这个问题已经有人解决过。按顺序逐级下降，不能跳级：

| 级别 | 来源 | 怎么查 | 通过条件 |
|---|---|---|---|
| 1 | 仓库内 | `npm run docs:where -- "关键词"`，再按模块页代码地图找同类函数/组件/接口/工具类 | 已有实现能直接复用或小改 |
| 2 | 已依赖的库/框架 | 查当前版本官方文档 | 原生支持，不靠记忆猜 API |
| 3 | 语言标准库 / 平台原生 | 官方文档 | 不需要额外依赖 |
| 4 | 成熟开源实现 | GitHub / 包管理器 / 技术社区 | 许可证兼容、近 12 个月有维护、无已知高危漏洞、体积可接受 |
| 5 | 改造或组合以上方案 | — | 比从零写成本低、风险小 |
| 6 | 从零手写 | — | 1–5 都不满足，且用户明确批准 |

### 1.2 什么算“实现”

- 算：新增功能、模块、接口、页面、算法、集成；新增文件；新增超过 30 行的逻辑；推倒重写现有模块。
- 不算：改错字、调样式、改配置值、重命名、在现有结构内的小修。
- 小修如果引入新算法、新协议、新依赖或新概念，仍算“实现”。
- 拿不准时按“算”处理。

### 1.3 调研证据

回复里写三行，不能只说“我查过了”：

1. 查了什么：关键词 + 来源（仓库 / 官方文档 / GitHub / 包管理器 / 技术社区）。
2. 找到什么：候选方案和链接。
3. 为什么选它，或为什么都不合适。

没有链接、没有候选、没有排除理由的“调研”视为没做。

### 1.4 从零实现审批

审批材料写清：

- 已排查的候选，以及每个候选被淘汰的具体原因；
- 自研范围和预计成本（文件、行数、依赖、维护点）；
- 现有方案不可用的原因：许可证 / 安全 / 性能 / 兼容 / 维护 / 体积；
- 怎么回滚。

用户明确同意后才能动手。只说“试试看”“你看着办”不算批准。

### 1.5 复用纪律

- 不复制来源不明、许可证不兼容的代码；优先加依赖，而不是把源码拷进仓库。
- 新增依赖同样要审批：用途、许可证、维护状态、体积和传递依赖、替代方案、移除成本。
- 不为一个小功能引入大框架；不引入与现有技术栈冲突的东西；版本必须锁定。
- 不用无 LICENSE、无 release、长期不维护的仓库。
- 复用不等于盲抄：要读接口、错误处理、边界条件，确认能接进现有架构。

### 1.6 查不到或断网

记录已尝试的查询和失败原因，列出候选，请用户决定；不许默默改成手写。

## 2. 注释

### 2.1 默认零注释

代码本身是主要文档：先用命名、类型、小函数把意图写清楚；注释不是装饰，也不是补救。

只允许两类：

1. **文件头**：一句话说明这个文件的代码负责什么。新建代码文件必须写；修改旧文件不强制补。
2. **函数/方法/组件头**：说明功能、参数、返回值/副作用，用该语言的标准文档格式（JSDoc / Javadoc / docstring），不写实现过程。

### 2.2 禁止的注释

- 解释代码“在做什么”的行内注释；
- 踩坑、历史、经验、结论、设计讨论；
- `TODO` / `FIXME` / `HACK`（写进 issue、提交信息或模块文档）；
- 注释掉的代码、变更日志、作者/日期签名；
- 用注释弥补命名或结构不清。

### 2.3 判定与例外

- 判定：删掉这条注释，代码是否仍然一目了然？是 → 删；否 → 先重命名、拆函数、改类型；还不够才写函数头。
- 不强制每个函数都写头：简单 getter/setter、显而易见的纯函数不写；Google Java Style 也明确“不言自明的成员”可以省略 Javadoc。
- why 写哪：业界常说“注释解释 why”，本项目不把 why 留在代码里；写进提交信息、ADR（[docs/decisions/](../decisions/)）或模块页。
- 例外：生成文件、第三方/vendor、许可证头、工具指令（如 eslint-disable、@ts-expect-error）不属于解释性注释，保留；生成文件不要手改；不支持注释的格式（JSON 等）不强行加。

### 2.4 示例

好的文件头：

```ts
// 权限目录的前端常量，由 PermissionEnum.java 生成。
```

好的函数头：

```ts
/** 返回当前用户可见的考试列表；无权限时返回空数组。 */
```

坏的注释：

```ts
// 遍历用户列表
for (const user of users) { ... }

// 这里必须用 useSSL=false，否则 MySQL 8 握手失败
```

第二类信息应写进提交信息、ADR 或 `docs/ops/`，不要留在代码里。

## 3. 测试

### 3.1 默认不写

- 不新增或修改测试文件、用例、fixture、mock、测试配置。
- 不把“补测试”当成交付的一部分；不要以 TDD 或覆盖率 为由写测试。
- 不新增“验证脚本”绕过本条：任何为了验证某段代码而新增的可重复执行脚本，都按测试处理。

### 3.2 允许并要求运行现有检查

按 [docs/start/testing.md](../start/testing.md) 跑：

- 前端：`npm run check`、`npm run build`；
- 后端：`./gradlew :api:compileJava`、`./gradlew :shared:test :rdbms:test :api:test`、`bootJar -x test`；
- 线上：`python scripts/nas/smoke-test.py`。

结果写进交付说明。没有测试不等于不编译、不检查。

### 3.3 现有测试失败

- 先报告失败项和原因，不许改测试让它变绿；
- 由用户决定改代码、改测试还是接受；
- 不删除、不跳过、不 `@Disabled` / `it.skip` 现有测试。

### 3.4 需要新测试时

先审批：测什么、为什么现有验证不够、放在哪里、维护成本。批准后再写。

### 3.5 验证替代

- 最小复现步骤；
- 真实请求/响应、日志、截图；
- 构建产物检查；
- 认证、权限、数据迁移这类高风险改动，必须额外跑现有冒烟并手工走一遍关键链路。

交付说明写清“验证了什么、没验证什么”。

## 4. 审批模板与自检

需要审批时按这个格式问，不许先做后说：

- 要做：
- 为什么现成方案不行：
- 影响范围：
- 替代方案：
- 怎么回滚：

只有用户在当次对话里明确说“同意 / 可以 / 批准”才算批准；沉默、超时、默认都不算。一次批准只覆盖当次范围，范围扩大要重新问。

开工前：

- [ ] 这次算“实现”吗？调研证据在哪？
- [ ] 要新增依赖、从零写、写测试吗？批准拿到了吗？

提交前：

- [ ] 新增注释是否只有文件头/函数头？
- [ ] 是否新增或修改了测试文件/验证脚本？
- [ ] 现有检查跑了吗？结果是什么？

## 5. 常见问题

**现有文件没有文件头，要补吗？**
不强制。新建文件必须写；修改旧文件只在本次触及的范围内补。

**公开 API 要不要 Javadoc？**
函数头允许，导出符号的契约要写；简单 getter/setter 不写。Google Java Style 对“不言自明的成员”有明确豁免。

**生成文件里有注释，违规吗？**
不违规。生成文件不要手改；要改就改生成器。

**现有测试失败，但不是我改坏的？**
报告失败项和证据；不要顺手改测试。由用户决定。

**安全漏洞很急，能不能先改再补审批？**
没有紧急例外。审批只是一句话，先问再做；不要借“紧急”绕过复用调研。

**30 行阈值怎么算？**
按新增或净增的逻辑行；格式化、移动代码不算。拿不准按“算”处理。

**可以从网上拷代码吗？**
可以复用，但要查许可证、维护状态和安全；优先加依赖；大段拷贝要审批。

**不写测试，怎么证明能跑？**
现有检查 + 手工复现 + 日志/截图；高风险路径跑冒烟。见 3.5。

**TDD 呢？**
本仓库不采用 TDD；不要以 TDD 为由写测试。

## 6. 依据

- Google Java Style Guide：Javadoc 对不言自明的成员可省略。https://google.github.io/styleguide/javaguide.html
- Google Python Style Guide：docstring 应描述契约，不复述代码。https://google.github.io/styleguide/pyguide.html
- Claude Code 文档：CLAUDE.md 是上下文注入，不保证严格遵从；规则要短。https://code.claude.com/docs/en/memory
- Cursor Rules：规则要具体、可判定，避免模糊。https://cursor.com/docs/context/rules
- AGENTS.md 指南：根文件保持短，按真实错误增补。https://www.morphllm.com/agents-md-guide
- LLM 生成回归测试的风险（预印本）：生成的测试可能把错误行为固化成预期。https://arxiv.org/abs/2610.11835
