# 版本与发版

> 面向维护者。**发版在 GitHub Actions 完成，本地不产出安装包**：本地只负责改写版本号、生成 CHANGELOG、打 tag；安装包由 tag `v*` 触发的 workflow 构建并挂到 GitHub Release。
>
> 用户侧的安装说明在根目录 [README.md](../../README.md)；本页讲"怎么把这个版本发出去"。

## 0. 一页速查

| 我要做什么 | 命令 / 位置 |
|---|---|
| 看下一个版本会是多少 | `.\scripts\release\Release.ps1 -DryRun -Bump auto` |
| 本地发版（改版本 + CHANGELOG + tag） | `.\scripts\release\Release.ps1 -Bump auto` |
| 推到 GitHub，让 Actions 构建并创建 Release | `.\scripts\release\Release.ps1 -Bump auto -Push` |
| 当前版本 | 根目录 `VERSION`（唯一真源） |
| 版本历史 | `CHANGELOG.md`（自动生成，勿手改历史段落） |
| 产物 | tag 推送后出现在 GitHub Release；本地没有 |

## 1. 版本规则

从 **2.0.0** 起使用[语义化版本](https://semver.org/lang/zh-CN/) `MAJOR.MINOR.PATCH`：

| 提交类型 | 递增位 | 例子 |
|---|---|---|
| `feat` | MINOR | 2.0.0 → 2.1.0 |
| `fix` / `perf` | PATCH | 2.0.0 → 2.0.1 |
| `BREAKING CHANGE`（正文或脚注） | MAJOR | 2.0.0 → 3.0.0 |
| `docs` / `chore` / `refactor` / `test` / `ci` / `style` / `build` | 不触发 | 只进 CHANGELOG 的分类或直接忽略 |

约定：

1. **`VERSION` 是唯一版本源**。`release.py bump` 会把同一个版本同步写进 `VERSION`、`CHANGELOG.md`、`client/package.json`、`server/pom.xml`；`server/api/src/main/resources/application.yml` 保留 `version: @projectVersion@` 占位符，由 Gradle 在构建时替换。Gradle、jar 名、安装包名、镜像 tag 都从它派生。**这几处都不要手改**，改了 `release.py check` 会报不一致。
2. **tag 形如 `vX.Y.Z`**（带 `v`），annotated tag；`.github/workflows/release.yml` 只对 `v*` 触发。
3. **`CHANGELOG.md` 由脚本生成**：新版本段落插在 `<!-- version list -->` 下面；手改会和下一次发版冲突。
4. **已发布的 tag 不移动**。发错了就发一个新版本（例如 2.0.1）或先删 Release 再把 tag 撤掉，见第 6 节。
5. **提交信息必须是 Conventional Commits**（`feat:` / `fix(scope):` / `feat!:` …）。版本是从提交算出来的，写成"修复了某某"就算不出版本。仓库自带 `commit-msg` 钩子（校验格式 + 去掉 AI 署名），首次克隆后装一次：

   ```powershell
   pwsh scripts/release/install-hooks.ps1      # Windows
   ```

   ```bash
   bash scripts/release/install-hooks.sh       # Linux / macOS
   ```

   临时绕过：`git commit --no-verify`（不建议，会让下一个版本号算错）。

## 3. 本地发版：只准备版本 + 打 tag

### 3.1 前置条件

- 改动已经**提交**；工作区干净（`git status` 为空）。默认拒绝在脏工作区发版，确有需要加 `-AllowDirty`。
- 本机有 Python 3（`release.py` 是 Python 脚本）。
- 你已经确认这次要发的是 MINOR 还是 PATCH——不确定就先 `-DryRun` 看一眼。

### 3.2 参数

| 参数 | 取值 | 说明 |
|---|---|---|
| `-Version` | `x.y.z` | 显式指定版本，跳过推导 |
| `-Bump` | `auto` / `major` / `minor` / `patch` / `none` | 默认 `auto`：按提交类型推导；`none` 表示不改版本（只补说明 / tag） |
| `-Notes` | 文件路径 | 用文件内容作为本版本的 CHANGELOG 说明（替代自动生成的条目） |
| `-Push` | 开关 | 提交并打 tag 后 push 到 GitHub（`origin main` + `vX.Y.Z`），触发 Actions。**只有加了这个才会构建发版** |
| `-NoTag` | 开关 | 只写版本文件（`VERSION` / `CHANGELOG.md` / `client/package.json` / `server/pom.xml`），不提交、不打 tag |
| `-DryRun` | 开关 | 只打印计划：会改成什么版本、动哪些文件、打什么 tag；不写文件、不提交、不推送 |
| `-AllowDirty` | 开关 | 允许工作区有未提交改动（默认拒绝）；带脏工作区时**只提交版本文件**，其他改动原样保留 |

Linux / macOS 用等价的 bash 入口 `scripts/release/release.sh`，参数一一对应：`--version` / `--bump` / `--notes` / `--push`（`-p`）/ `--no-tag` / `--dry-run` / `--allow-dirty`。

`Release.ps1` 本身不打包、不跑 Gradle、不碰 `docker`：

- 检查工作区是否干净 → `release.py plan` 算版本 → `release.py bump` 写版本文件 → `release.py check` 校验一致 → `release.py tag` 提交并打 tag →（`-Push` 才 push）。
- 需要 Python 3.8+ 在 `PATH` 里；`Release.ps1` 找不到 `python` 会直接报错。

### 3.3 常用命令

```powershell
# 1) 预演：看会升到哪个版本、CHANGELOG 会多出什么
.\scripts\release\Release.ps1 -DryRun -Bump auto

# 2) 正式发版（本地）：改 VERSION、写 CHANGELOG、提交、打 tag vX.Y.Z
.\scripts\release\Release.ps1 -Bump auto

# 3) 指定版本（不靠推导）
.\scripts\release\Release.ps1 -Version 2.0.0

# 4) 不改版本号，只补一个发布说明
.\scripts\release\Release.ps1 -Bump none -Notes .\release-notes\2.0.0.md

# 5) 推到 GitHub：trigger Actions，构建产物 + 创建 Release
.\scripts\release\Release.ps1 -Bump auto -Push
```

如果 tag 已经打好、只是忘了推：

```powershell
git push origin v2.0.0
```

`release.py` 的子命令可以直接调用（行为以 `python scripts/release/release.py <cmd> --help` 为准）：

| 子命令 | 常用参数 | 作用 |
|---|---|---|
| `plan` | `--bump`、`--json`、`--print-version` | 算下一个版本（不改文件）；`--print-version` 只输出 `x.y.z`，供脚本取值 |
| `check` | `--tag` | 校验 `VERSION` / `CHANGELOG.md` / `client/package.json` / `server/pom.xml` 版本一致，并确认 `application.yml` 仍是 `@projectVersion@` 占位符；加 `--tag` 再校验 HEAD 的 tag |
| `bump` | `--version`、`--bump`、`--notes` | 把新版本写进上述文件，并把版本段落插到 `CHANGELOG.md` 的 `<!-- version list -->` 下 |
| `tag` | `--version` | 提交版本文件、创建 `vX.Y.Z` tag（**不 push**） |
| `notes` | `--version`、`--out` | 从 CHANGELOG 抽出版本段落，生成发布说明（Actions 用它产出 `RELEASE_NOTES.md`） |
| `commits` | `--since` | 列出上个 tag 以来的 conventional commits，排查"为什么没升版本"用 |

### 3.4 本地发版做完之后

1. `git log --oneline -3` 应看到版本提交；`git tag --list "v*" | tail` 能看到新 tag。
2. 推送 tag（`-Push` 或手动 `git push origin vX.Y.Z`）后，去 Actions 看 `release` workflow。
3. workflow 成功后，Release 页面应挂上第 4 节的四类产物 + `SHA256SUMS` + `RELEASE_NOTES.md`。

## 4. 产物清单（由 Actions 生成）

| 文件 | 内容 | 给谁 |
|---|---|---|
| `xuri-classroom-<version>-windows-x64.zip` | Windows 便携包（不含 JRE / MySQL，首次启动下载） | 单机 Windows 用户 |
| `xuri-classroom-<version>-linux-x64.tar.gz` | Linux 安装包（`install.sh` / `uninstall.sh` / jar / 初始化 SQL） | Linux 服务器 |
| `xuri-classroom-<version>-docker.tar.gz` | Docker **部署包**：`docker-compose.release.yml` + `.env.example` + `README.md` + `Dockerfile.runtime` + `VERSION` + jar + `init-mysql.sql`（**不是** `docker save` 的镜像 tar） | 内网 / 离线 Docker |
| `xuri-classroom-<version>.jar` | 可独立运行的 Spring Boot jar（SPA 已内嵌） | 已有 MySQL 的裸机 / 自己写服务脚本 |
| `SHA256SUMS` | 上面所有文件的校验和 | 校验下载完整性 |
| `RELEASE_NOTES.md` | 本次版本说明（来自 CHANGELOG） | 发通知 / 贴群 |

### 4.1 Windows 便携包

约 80MB（jar 约 78MB；不含 JRE / MySQL）。`package.py` 组装时要求模板里有 `start.cmd`、`setup.cmd`、`doctor.cmd`、`lib/launcher.ps1`，缺一个就打包失败。

包内布局：

```text
start.cmd  stop.cmd  status.cmd  setup.cmd  doctor.cmd
README.txt  VERSION
app/xuri-classroom-<version>.jar
app/init-mysql.sql
config/app.env.example      # 应用配置（端口、数据库、JWT 密钥）
config/runtime.env.example  # 运行时下载地址（JRE / MySQL 镜像）
lib/launcher.ps1
```

首次**双击 `setup.cmd`** 时，`lib/launcher.ps1` 会（之后日常用 `start.cmd`）：

1. 生成 `config/app.env`（随机 DB 密码、随机 JWT 密钥、`PORT=8080`），已存在则保留。
2. 缺 JRE 8 就下载 JRE 8u512b09（Adoptium 构建，清华 TUNA 镜像，回退南大镜像；约 38MB）到 `cache/`，校验后解压到 `runtime/jre8/`。
3. 缺 MySQL 就下载 MySQL 8 压缩包（优先华为/阿里镜像的 8.0.28，约 212MB；失败回退官方 8.0.44，约 233MB），校验 SHA256、解压裁剪到 `mysql/`。
4. 首次初始化内置 MySQL：`mysqld --initialize-insecure` → 临时启动 → 建库 `surveyking` 与用户 `xuri` → 导入 `app/init-mysql.sql` → 设 root 随机密码 → 停临时实例。
5. 用 `runtime/jre8/bin/java.exe` 启动 `app/*.jar`，写日志到 `logs/`、PID 到 `run/`。
6. 轮询 `/api/system` 就绪后打开浏览器，并打印局域网访问地址。

运行期目录（首次启动后出现）：

| 目录 | 内容 |
|---|---|
| `data/mysql/` | 内置 MySQL 数据目录（**备份它**） |
| `data/files/` | 上传的附件（**备份它**） |
| `logs/` | 应用与 MySQL 日志 |
| `run/` | PID 文件 |
| `cache/` | 下载的 JRE / MySQL 压缩包（可删，删了会重下） |
| `runtime/jre8/`、`mysql/` | 解压后的运行时（可删，删了会重解压/重下） |

命令：

| 命令 | 作用 |
|---|---|
| `start.cmd` | 日常启动；未安装时会自动进入引导 |
| `stop.cmd` | 停止 Java 与内置 MySQL |
| `status.cmd` | 打印端口、PID、访问地址 |
| `setup.cmd` | 引导安装（4 步：环境检查 / JRE / MySQL / 启动），可重复执行；支持 `--whatif`、`--step env\|jre\|mysql\|db\|app`、`--offline` |
| `doctor.cmd` | 自检：Java、MySQL、端口、目录权限、日志位置；`--fix` 尝试自动修复 |

端口默认 **8080**（`config/app.env` 的 `PORT`）；内置 MySQL 只监听 `127.0.0.1:3307`，不对外。

**离线安装**：把 JRE / MySQL 压缩包放进 `cache/`（文件名与 `config/runtime.env` 里一致），或改 `config/runtime.env` 指向内网镜像。包内 `README.txt` 是给最终用户的版本，二者冲突时以包内为准。

**升级**：停服务 → 用新包覆盖程序文件（`app/`、`lib/`、`*.cmd`），**保留** `data/`、`config/`、`mysql/`、`runtime/` → 启动。升级前先备份 `data/`。

### 4.2 Linux 安装包

```bash
tar -xzf xuri-classroom-<version>-linux-x64.tar.gz
cd xuri-classroom-<version>
sudo bash install.sh --port 8080 --db-password '改成强密码'
```

脚本只支持 bash（`sh install.sh` 会失败）；解压后 `install.sh` 带执行位，`sudo ./install.sh …` 也可以。

`install.sh` 参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--port` | `8080` | 应用端口（`SERVER_PORT`） |
| `--install-dir` | `/opt/xuri-classroom` | 安装目录 |
| `--user` | `xuri` | 运行服务的系统用户 |
| `--db-host` / `--db-port` | `127.0.0.1` / `3306` | MySQL 地址 |
| `--db-name` / `--db-user` | `surveyking` / `surveyking` | 库名与连接账号 |
| `--db-password` | 无（必填，交互询问） | 连接密码；也可用环境变量 `XURI_DB_PASSWORD` |
| `--db-admin-user` / `--db-admin-password` | `root` / 空 | 仅 `--init-db` 建库时用的管理员账号 |
| `--init-db` | 关 | 用本机 `mysql` 客户端建库、建用户、授权并导入 `app/init-mysql.sql`（只允许空库；缺客户端会明确报错） |
| `--download-jre` | 关 | 从清华 TUNA（回退南大）下载 Temurin JRE 8 到 `runtime/jre8/`；包本身不含 JRE |
| `--no-jre` | 关 | 强制用系统 `java`（与 `--download-jre` 互斥） |
| `--no-systemd` | 关 | 只准备目录与配置，不写 unit、不启动；检测不到 systemd 时会自动降级到这个模式 |
| `--yes` / `-y` | 关 | 非交互 |
| `--help` | — | 用法 |

安装后：

| 路径 | 内容 |
|---|---|
| `/opt/xuri-classroom/app.jar` | 应用 |
| `/opt/xuri-classroom/app.env` | 配置（`0600`）：`DB_*`、`SERVER_PORT`、`TZ`、`JAVA_TOOL_OPTIONS`、`SK_JWT_SECRET`、`SK_WEB_SPA_ENABLED=true`、`FILE_STORAGE_LOCAL_ROOT_PATH`、`SPRING_DATASOURCE_*`（pro 包需要；安装器按 DB_* 自动同步） |
| `/opt/xuri-classroom/files/` | 上传附件（**备份它**） |
| `/opt/xuri-classroom/logs/` | 日志 |
| `/opt/xuri-classroom/runtime/jre8/` | 可选，`--download-jre` 才有 |

服务名 `xuri-classroom`（`/etc/systemd/system/xuri-classroom.service`）：

```bash
systemctl status xuri-classroom
journalctl -u xuri-classroom -f
```

**幂等**：重复执行 `install.sh` 会保留已有 `app.env` 与 `SK_JWT_SECRET`，只更新命令行显式给出的值，并重启服务——这就是升级方式。**卸载**：`sudo bash uninstall.sh`（默认保留安装目录与数据），`--purge` 才删目录与用户。

### 4.3 Docker

镜像与部署包是两件事：

- **镜像**：workflow 推到 GHCR，`ghcr.io/hermannmayer/xuri-classroom:<version>` 与 `:latest`。
- **`docker.tar.gz`**：部署包（compose / `.env.example` / README / `init-mysql.sql`），**不是**镜像 tar。

```bash
# 1) 解压部署包（或直接用仓库的 docker/ 目录）
tar -xzf xuri-classroom-<version>-docker.tar.gz
cd docker
cp .env.example .env        # 改 DB_PASSWORD、JWT_SECRET、APP_PORT、VERSION

# 2) 起服务（app 会拉 GHCR 镜像）
docker compose -f docker-compose.release.yml up -d
```

也支持一行脚本：`curl -fsSL https://raw.githubusercontent.com/Hermannmayer/xuri-classroom/main/scripts/deploy/docker-one-line.sh | sudo bash`（环境变量 `XURI_HOME` / `APP_PORT` / `VERSION`；国内可加 ghproxy 前缀，第三方代理有风险）。

| 项 | 值 |
|---|---|
| compose 文件 | `docker-compose.release.yml`（项目名 `xuri-classroom`；`app` + `mysql:8.0`） |
| 镜像 | `ghcr.io/hermannmayer/xuri-classroom:<tag>`；`.env` 的 `VERSION` 决定 tag，`XURI_IMAGE` 可换成国内镜像源（如 `ghcr.nju.edu.cn/hermannmayer/xuri-classroom`） |
| 端口 | `APP_PORT`，默认 `8080` |
| 数据卷 | `xuri-classroom-db-data`（MySQL）、`xuri-classroom-app-files`（附件，固定卷名，备份不用猜前缀） |
| 必填变量 | `DB_PASSWORD`、`JWT_SECRET`（compose 用 `:?` 强制，缺了直接拒绝启动） |
| 初始化 | 首次启动由 `mysql` 容器执行 `init-mysql.sql`（`INIT_SQL_FILE` 可换路径；**只对空卷**） |

**离线安装**：在有网机器 `docker pull` → `docker save -o xuri-classroom-<version>.tar ghcr.io/hermannmayer/xuri-classroom:<version>` → 拷到目标机 `docker load -i`；`mysql:8.0` 同样处理。

升级：改 `.env` 的 `VERSION` 后 `docker compose -f docker-compose.release.yml pull app && docker compose -f docker-compose.release.yml up -d`。备份/回滚与 GHCR 细节以 `docker/README.md` 为准。

### 4.4 只有 jar

```bash
java -jar xuri-classroom-<version>.jar --server.port=8080
```

需要环境变量（或同名 `--参数`）：`SPRING_DATASOURCE_URL`、`SPRING_DATASOURCE_USERNAME`、`SPRING_DATASOURCE_PASSWORD`、`SK_JWT_SECRET`、`SK_WEB_SPA_ENABLED=true`、`FILE_STORAGE_LOCAL_ROOT_PATH`。库要先按 `init-mysql.sql` 初始化（空库）。完整变量表见 [环境变量](../reference/env.md)。

## 5. GitHub Actions

- **触发**：`push` 一个 `v*` tag（`Release.ps1 -Push` 或 `git push origin vX.Y.Z`）。分支推送不会触发发版，只跑 `docs.yml`；也支持手动 `workflow_dispatch`（输入已存在的版本号，用于重跑某个 tag）。
- **做什么**：构建可执行 jar（`-Ppro`，前端用 `-PwithSpa` 内嵌）→ `package.py` 组装 Windows zip / Linux tar.gz / Docker 部署包 + 单独 jar → 推 GHCR 镜像 → 生成 `SHA256SUMS` 与 `RELEASE_NOTES.md` → 创建 GitHub Release 并上传全部 assets。
- **看结果**：仓库 Actions → `Release` workflow → 最近一次 run（作业：校验版本 → 构建 SPA jar → Windows / Linux / Docker 打包 → GHCR 镜像 → 创建 Release）；成功后 Release 页可直接下载。
- **失败重跑**：用 run 页面里的 "Re-run jobs"。tag 不变，重跑不会改版本号。
- **不要**在 Actions 里改版本号：版本只有 `VERSION` 一个来源，改版本必须走 `release.py`。

## 6. 回滚

| 场景 | 做法 |
|---|---|
| 装错版本（Windows） | 停服务 → 换回上一版本目录（或把 `app/` 换回旧 jar）→ 启动；`data/` 不动 |
| 装错版本（Linux） | 重新解压上一版本 tar.gz → `sudo bash install.sh`（保留 `app.env` 与 `SK_JWT_SECRET`）→ `systemctl restart xuri-classroom` |
| 装错版本（Docker） | 改 `.env` 的 `VERSION` 为旧版本 → `docker compose -f docker-compose.release.yml up -d` |
| Release 发错 | GitHub 上把 Release 标成 pre-release 或删除；镜像/包不要改名重发 |
| tag 必须撤 | `git tag -d vX.Y.Z` + `git push origin :refs/tags/vX.Y.Z`，然后发一个新的 patch 版本说明原因。**已有人下载过的包不要假装没发生** |
| 代码有问题 | `git revert <坏提交>` → 按第 3 节发一个 patch 版本（不要移动旧 tag） |
| 数据被改坏 | 用备份恢复（第 7 节）；`scripts/nas/migrate/**` 只升不降，不能靠"再跑一遍"回退 |

NAS 线上的回滚是另一条线（`scripts/nas/Deploy-Nas.ps1` + 旧容器），见 `docs/ops/NAS-开发工作流.md`。

## 7. 数据与备份（发版相关）

- **数据在哪**：Windows `data/mysql` + `data/files`；Linux `/var/lib/mysql`（外部实例）+ `/opt/xuri-classroom/files`；Docker 卷 `xuri-classroom-db-data` + `xuri-classroom-app-files`。
- **升级前必须备份**：`mysqldump --single-transaction --databases surveyking` + 打包附件目录。
- **`init-mysql.sql` 只对空库执行**（开头 25 处 `DROP TABLE IF EXISTS`）。有数据的库升级只能跑 `scripts/nas/migrate/*.sql`。
- 恢复顺序：停服务 → 建空库 → 导入 `db.sql` → 解包附件 → 启动 → 抽查列表/答卷能否打开。

## 8. 常见错误

| 现象 | 原因 | 处理 |
|---|---|---|
| `VERSION` 与 tag / 包名 / 镜像 tag 不一致 | 有人手改了 `VERSION`，或绕过 `release.py` 直接打 tag | 以 `VERSION` 为准重发；检查 `release.py plan` 的输出 |
| 发完版本号没变 | `-Bump none`，或自上个 tag 以来没有 `feat`/`fix`/`perf` | 用 `-Bump patch`（或 `minor`）显式指定 |
| 发版被拒：工作区不干净 | 有未提交改动 | 先提交；确认要带着脏工作区发才用 `-AllowDirty` |
| `找不到 python` | 本机没有 Python 3.8+ 或不在 `PATH` | 装 Python 并确认 `python --version` 可用 |
| `release.py check` 报版本不一致 | 手改了 `VERSION` / `client/package.json` / `server/pom.xml` / `application.yml` 之一 | 不要手改；让 `release.py bump --version x.y.z` 统一写一遍 |
| 提交被 git 拒绝（commit-msg 钩子） | 提交信息不是 Conventional Commits | 改成 `feat: …` / `fix(模块): …`；确需绕过加 `--no-verify` |
| `docker compose` 拒绝启动：`请在 .env 里设置 DB_PASSWORD / JWT_SECRET` | compose 用 `:?` 强制这两个变量 | 在 `.env` 里填真实值（`openssl rand -base64 48`） |
| 拉不到 GHCR 镜像（超时 / unauthorized） | 访问不了 `ghcr.io` | 配镜像加速，或在 `.env` 设 `XURI_IMAGE=ghcr.nju.edu.cn/hermannmayer/xuri-classroom`；离线走 `docker save/load` |
| `tag already exists` | 该版本已打过 tag | 不移动旧 tag；改版本号（`-Bump patch`）重新发 |
| 起不来：端口被占（8080） | 上一次没停干净，或别的服务占了 | Windows：`netstat -ano \| findstr :8080` → 结束进程或改 `config/app.env` 的 `PORT`；Linux：`ss -lntp \| grep 8080` → 改 `--port`；Docker：改 `.env` 的 `APP_PORT` |
| MySQL 初始化失败（Windows 首次） | 密码含特殊字符、`data/mysql` 里有半初始化的残留、3307 被占 | 看 `logs/`；删 `data/mysql` 重新初始化（**会丢数据**）；确认 3307 没被占用 |
| MySQL 初始化失败（Linux `--init-db`） | `mysql` 客户端不在、root 密码错、库已存在且有数据 | 脚本会明确报错且不启动服务；改用外部库或手工建库后重跑 |
| 首次下载失败 | 网络不通、镜像不可达、SHA256 不匹配 | 重试 `setup.cmd`；或把压缩包放进 `cache/`；或改 `config/runtime.env` 换镜像 |
| 页面白屏 / 404 | `SK_WEB_SPA_ENABLED` 不是 `true`，又没配 nginx | 发布包必须 `SK_WEB_SPA_ENABLED=true`；NAS 形态才用 nginx |
| 重启后所有人掉线 | 没配 `SK_JWT_SECRET`，每次启动随机 | 在 `app.env`/`.env` 里配 `SK_JWT_SECRET`（`openssl rand -base64 48`） |
| curl 登录报"账号或密码错误" | 登录密码走 RSA 加密（`/api/system` 的 `publicKey`） | 用浏览器或脚本先取公钥；不要发明文 |
| 升级后接口 500（`Unknown column`） | 没跑对应的 `scripts/nas/migrate/*.sql` | 先迁移再启动；顺序见各迁移脚本头部注释 |
| Actions 构建失败 | 依赖缓存失效、下载 JRE/MySQL 超时 | 看 run 日志；重跑；必要时在 workflow 里换镜像地址 |

## 10. 与 NAS 发布、源码构建的关系

- **NAS 线上**不经过 GitHub Release：`scripts/nas/Deploy-Nas.ps1` 从 `nas` 远端部署，仍是 nginx + app + db 三容器形态，前端由 nginx 卷提供。两套流程只在"同一个提交"这一点上一致。
- **从源码构建（维护者）**：仓库根目录的 `docker-compose.yml` + `Dockerfile` 是开发/自建路径（nginx 80 + app 7007 + db，对外 `APP_PORT` 默认 9527），需要 Node 20 与 JDK 8 的构建环境。它**不是**用户安装方式，README 面向用户的 Docker 章节只讲 `docker/docker-compose.release.yml`。
